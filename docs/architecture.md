# Архитектура

## Компоненты

| Компонент | Технологии | Ответственность |
|---|---|---|
| UI | React 19, Vite, TypeScript | выбор ТС/проверки, вердикт, чат, заявка, парк |
| API | FastAPI, Pydantic | HTTP-контракт, сборка контекста, отдача SPA |
| Агент | OpenAI-совместимый API (tool calling) | выбор инструментов и формулировка ответа |
| RAG | PyMuPDF, BM25, Snowball | поиск нормативов с привязкой к странице PDF |
| Хранилище | SQLite | ТС, проверки, сообщения, заявки |
| Моки | FastAPI (стенды организаторов) | Mock ML `/diagnose`, Mock ТОиР `/tickets` |
| Публикация | Docker Compose, Caddy | HTTPS, единый origin для UI и API |

## Поток запроса

```
Механик → UI → POST /api/chat
                 │
                 ├─ store: ТС + выбранная проверка (жёсткая привязка контекста)
                 ├─ LLM: сообщение + история диалога + описания инструментов
                 │    ├─ get_diagnosis → Mock ML /diagnose
                 │    ├─ search_manuals → BM25 (фильтр по двигателю ТС)
                 │    ├─ get_vehicle_history → SQLite
                 │    ├─ get_fleet_overview → SQLite
                 │    └─ create_ticket → валидация → Mock ТОиР /tickets → SQLite
                 └─ ответ: текст + след инструментов (tool_calls)
```

Агент работает до 8 шагов. История диалога хранится по `conversation_id` (последние
10 сообщений), поэтому уточняющие вопросы не теряют контекст.

## Инструменты и контракты

| Инструмент | Вход | Выход | Ограничения |
|---|---|---|---|
| `get_diagnosis` | — | статус, тип, score, confidence, quality, description | ТС и проверка берутся из контекста, подменить нельзя |
| `search_manuals` | `query` | фрагменты: `manual`, `pdf_page`, `text` | только документы двигателя этого ТС |
| `get_vehicle_history` | — | проверки и заявки ТС | только текущий ТС |
| `get_fleet_overview` | — | корзины парка и приоритетный список | агрегаты по SQLite |
| `create_ticket` | тип, заключение, срочность, работы, запчасти, ссылки | `ticket_id` | только `anomaly`; тип совпадает с проверкой; ссылки — из выдачи поиска |

Модель не может передать `vehicle_id` или `session_id` в инструменты: они привязаны к
контексту запроса на сервере. Это исключает диагностику «чужого» ТС и заявку не по той
проверке.

## Почему не if/else

Сценарий не разложен на ветки «если F01 — рассказать про клапаны». Модель сама решает,
что вызвать: при `check_failed` достаточно `get_diagnosis`, при вопросе про момент затяжки —
`search_manuals`, при просьбе о заявке — поиск плюс `create_ticket`. Код фиксирует только
набор инструментов, их контракты и правила безопасности; добавление нового типа
неисправности или документа не требует правок логики.

## Защита от ошибок модели

1. **Диагноз — только из сервиса.** Значения статуса, типа и уверенности нельзя взять
   из текста: инструмент возвращает их из Mock ML, правило в системном промпте запрещает
   придумывать.
2. **Нормативы — только из руководства.** Каждое техническое утверждение должно иметь
   ссылку на документ и страницу из выдачи поиска.
3. **Жёсткий фильтр по двигателю.** BM25 ищет только в документах, зарегистрированных
   за двигателем ТС; ссылки на чужие руководства отклоняются и при создании заявки.
4. **Серверная валидация заявки.** `anomaly_type` сверяется с проверкой, списки непустые,
   документ принадлежит двигателю, страница существует, страница была в результатах
   поиска в этом запросе.
5. **Заявка — только по просьбе.** `create_ticket` отклоняется, если в сообщении механика
   нет явной просьбы («оформи заявку», «передай в ТОиР», «нужна дефектовка»): модель не
   должна создавать заявку «на всякий случай» в ответ на технический вопрос.
6. **Отказ при нехватке данных.** Для `check_failed` правило запрещает выводы о двигателе;
   для вопросов вне базы знаний — честное «в базе знаний нет данных».
7. **Сбои LLM не ломают интерфейс.** Запрос повторяется до трёх раз на 429/5xx/сетевых
   ошибках; если модель недоступна, `/api/chat` отвечает 503 с понятным текстом, а экраны
   парка и карточки ТС продолжают работать.

## Данные

```
vehicles      vehicle_id PK, garage_no, make, model, engine_model, fuel
sessions      session_id PK, vehicle_id, checked_at, status, anomaly_type,
              anomaly_score, confidence, signal_quality, description
messages      conversation_id, vehicle_id, role, content, created_at
tickets       ticket_id PK, vehicle_id, session_id, anomaly_type, urgency,
              conclusion, operations JSON, spare_parts JSON, references JSON
```

`vehicles` и `sessions` заполняются из `data/vehicles.json` при первом старте. Заявки
пишутся после успешного ответа Mock ТОиР, поэтому `ticket_id` в UI всегда настоящий.

## Развёртывание

```
Caddy (443, Let's Encrypt) → 127.0.0.1:8090 → контейнер api
                                              ├─ mock_ml   (внутренняя сеть)
                                              └─ mock_toir (внутренняя сеть)
```

- `manuals/` монтируется read-only; PDF не попадают ни в git, ни в образ.
- `data/` монтируется с хоста: индекс и SQLite переживают перезапуск.
- Индекс строится entrypoint'ом при первом старте, если `data/index/bm25.pkl` отсутствует.
- Секреты — только в `.env` на сервере (права 600), в образ не копируются.
