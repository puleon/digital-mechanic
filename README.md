# Цифровой механик

AI-агент, который превращает результат акустической диагностики двигателя в понятное
решение механика: объясняет отклонение по руководству (с документом и страницей PDF),
отвечает на вопросы по ремонту и оформляет заявку на дефектовку в ТОиР.

Хакатон «ИИкузница», трек «Цифровой механик» (ООО «НейроДВС»), 26–28.11.2026.

**Демо:** <https://digital-mechanic.128-0-134-250.sslip.io>

## Что умеет

- **Вердикт за 10 секунд.** Выбор ТС и проверки → кнопка «Получить результат диагностики» →
  карточка со статусом (`normal` / `anomaly` / `check_failed`), типом F01–F14, уверенностью,
  качеством записи и понятным описанием.
- **Три состояния — три разных сценария.** При `check_failed` агент не делает выводов о
  двигателе и просит повторить запись; при `normal` не создаёт заявку; при `anomaly`
  объясняет причину и предлагает дефектовку.
- **RAG по руководствам.** Ответы только по PDF руководств для двигателя этого ТС,
  с ссылками вида `236.01.01 РК, стр. 269`. Нет данных в базе — агент честно отказывается.
- **Заявка в ТОиР.** По явной просьбе механика: работы, запчасти, срочность и ссылки на
  руководство → `ticket_id` от Mock ТОиР.
- **Память и история.** Проверки и заявки хранятся в SQLite, диалог помнит контекст,
  график показывает динамику `anomaly_score`.
- **Парк.** Сводка по 50 ТС: норма / внимание / карантин, переход к карточке ТС одним касанием.
- **Прозрачность.** Раскрывающийся след вызовов инструментов: что искал агент и что получил.

## Архитектура

```
┌──────────────────────────────┐
│ React + Vite (мобильный UI)  │
└──────────────┬───────────────┘
               │ /api/chat, /api/vehicles, /api/fleet
┌──────────────▼───────────────┐
│ FastAPI                      │
│  ├─ агент: tool calling      │  get_diagnosis · search_manuals · get_vehicle_history
│  │                           │  get_fleet_overview · create_ticket
│  ├─ RAG: BM25 + фильтр       │  чанки привязаны к doc_id и странице PDF
│  ├─ SQLite                   │  проверки, сообщения, заявки
│  └─ клиенты Mock ML / ТОиР   │  адреса только из .env
└──────────────────────────────┘
```

Сценарий не зашит в `if/else`: LLM сама выбирает инструмент, сервер лишь ограничивает
контракт и проверяет данные перед записью. Подробнее — [docs/architecture.md](docs/architecture.md).

## Быстрый старт (Docker, ~5 минут)

Нужен Docker с Compose. PDF руководств в репозиторий не входят — положите их в `manuals/`
(имена файлов фиксированы, см. `backend/app/rag/manuals.py`):

```
manuals/
├── ЯМЗ_236_руководство по эксплуатации.pdf
├── ЯМЗ_236_руководство по РЕМОНТУ.pdf
├── yamz-536_re_2016.pdf
├── yamz-536_rk_2013.pdf
├── zmz-5234_rk_2025.pdf
└── zmz-40904-40905_rk_2025.pdf
```

```bash
git clone https://github.com/puleon/digital-mechanic.git
cd digital-mechanic
cp .env.example .env              # вписать LLM_API_KEY
# положить PDF в manuals/
docker compose up -d --build      # первый старт: сборка + индекс ~1–2 мин
curl http://localhost:8090/api/health
```

Открыть <http://localhost:8090>. При первом старте контейнер сам строит поисковый индекс
по PDF (~15 секунд, 1743 страницы, ~3500 чанков). Логи: `docker compose logs -f api`.

## Локальная разработка

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r backend/requirements.txt
.venv/bin/python backend/scripts/ingest.py          # index в data/index/
```

Терминал 1–2 — моки организаторов:

```bash
MOCK_DATA_PATH=$PWD/data/vehicles.json .venv/bin/uvicorn mock_ml.app:app   --app-dir mocks --port 8001
MOCK_DATA_PATH=$PWD/data/vehicles.json .venv/bin/uvicorn mock_toir.app:app --app-dir mocks --port 8002
```

Терминал 3 — API, терминал 4 — UI:

```bash
.venv/bin/uvicorn app.main:app --app-dir backend --port 8091
cd frontend && npm install && npm run dev           # http://localhost:5173, proxy /api → 8091
```

Проверка поиска без LLM:

```bash
.venv/bin/python backend/scripts/search.py "момент затяжки осей коромысел" --engine ЯМЗ-236М2
```

## Переменные окружения

| Переменная | Назначение | Пример |
|---|---|---|
| `MOCK_ML_URL` | сервис диагностики | `http://127.0.0.1:8001` |
| `MOCK_TOIR_URL` | сервис ТОиР | `http://127.0.0.1:8002` |
| `LLM_BASE_URL` | OpenAI-совместимый API | `https://api.proxyapi.ru/v1` |
| `LLM_API_KEY` | ключ (только на сервере, не в git) | `sk-…` |
| `LLM_MODEL` | модель | `deepseek/deepseek-v4.1-flash-1017` |
| `DATA_DIR` | данные и SQLite | `./data` |
| `MANUALS_DIR` | PDF руководств | `./manuals` |

В Docker адреса моков переопределяются на имена сервисов compose; ключ передаётся
через `.env` и никогда не попадает в образ или репозиторий.

## Как устроен поиск по руководствам

1. **Извлечение.** PyMuPDF постранично; удаляются колонтитулы и номера страниц,
   склеиваются переносы слов.
2. **Нарезка.** Чанки не пересекают границы страницы (иначе номер страницы в ссылке
   становится неоднозначным), ~700 символов, максимум 1100.
3. **Индекс.** BM25 + стемминг Snowball (русский). Жёсткий фильтр: ищутся только документы
   двигателя текущего ТС — нормативы другого двигателя физически не попадают в выдачу.
4. **Цитаты.** В контекст и в ответ идут канонические обозначения документов и **номер
   страницы PDF** (как требует ТЗ), а не печатный номер.
5. **Контроль.** `create_ticket` принимает только те страницы, которые реально были
   в результатах `search_manuals` этого запроса; выдуманная ссылка отклоняется сервером.

Метрики и контрольный набор вопросов — [docs/rag-quality.md](docs/rag-quality.md).

## Ограничения

- Mock ML и Mock ТОиР — стенды организаторов; в проде заменяются реальными сервисами
  без изменения кода (адреса в `.env`).
- Ответы LLM вероятностные: агент ограничен правилами и серверной валидацией, но
  перед реальным ремонтом нужна дефектовка.
- У прототипа нет аутентификации; стенд демонстрационный.

## Данные и права

`data/vehicles.json` и `data/fault_types.json` — синтетические материалы хакатона.
PDF руководств являются собственностью правообладателей: они не включены в репозиторий
и не распространяются, на стенде лежат вне git.
